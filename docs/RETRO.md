# 经验复盘（RETRO）

本轮范围：B 站线索二次反查与终态收敛、付费补录与许可盲区、报告口径固化、`scripts/recheck.js` 可重跑复核。
写法：现象 → 根因 → 可复用规则 → 下次具体怎么做。规则已回流到脚本或 README 的，逐条注明位置。

## 1. B 站搜索页与字幕：拿不到就是拿不到

- **现象**：`WebFetch` 打开 B 站搜索结果页只有页脚/框架；`player/v2` 匿名字幕列表全部为空。
- **根因**：搜索结果是前端 JS 渲染；字幕接口在匿名态不返回，UP 字幕与 AI 字幕都需要登录态 Cookie。
- **可复用规则**：发现视频用公开检索定位 BV 号，再用 `view` 接口取元数据；字幕拿不到就写「未获取（需登录 Cookie）」，不猜、不下载视频、不做 ASR。
- **下次怎么做**：只用 `view/reply/player` 公开接口；每条视频保留 `subtitleStatus` 与抓取时间；`build.js` 已校验字幕非空与时间戳合法。

## 2. Fab 403：不绕过，换公开渠道

- **现象**：Node/脚本直连 Fab 常 403 或 Cloudflare 挑战页；同一 listing 换 `?lang=` 参数又会 404。
- **根因**：站点有反爬与路由缓存差异，免费手段无法稳定拿 HTML。
- **可复用规则**：403/429/503 一律记「风控，未获取」，保持原状态；人工核对用可打开的公开页面文本，并把证据链接写进 `recheck-evidence.json`；绝不用代理绕过。
- **下次怎么做**：先跑 `node scripts/recheck.js`（自动跳过风控）；对拿不到的条目走公开检索/卖家页/作者主页人工核对，结论写回 evidence，再跑 `node scripts/build.js`。

## 3. 失效判定：404 不等于资源没了

- **现象**：`Interactive Foliage Physics` 曾因 `?lang=en-US` 404 被判死链，裸 URL 实际可打开且标 Free。
- **根因**：Fab 路由/缓存不稳定；单次请求结果不能代表资源状态。
- **可复用规则**：只有「稳定 404/410 或页面明确 Sorry, we couldn't find that page」才判 `removed/dead`；一次 404 必须换渠道复核；判定必须带证据链接与核对日期。
- **下次怎么做**：`recheck.js` 已限定 404/410/软 404 才改判；人工复核优先看卖家页与商品页两种入口；改判前保留原状态到 `changes` 报告。

## 4. 去重聚合：状态冲突要有优先级

- **现象**：同一资源被多条视频提及，出现「免费」「已收费」「待核实」互相冲突；按先到先得会得到错误结论。
- **根因**：缺少统一的状态优先级，聚合只做了名称/URL 去重。
- **可复用规则**：按 `normUrl(officialUrl)`，否则 `name:` 聚合；状态取 `verified > paid > removed > dead > pending`；最终状态回写 `free`（verified→true，paid/removed/dead→false）。
- **下次怎么做**：新增线索后先跑 `node scripts/build.js` 看 `bilibili-pending.json` 是否收敛；冲突时以有证据链接的强结论为准，并在 `note` 写清渠道。

## 5. 构建校验：把口径写进脚本，不靠人记

- **现象**：早期状态只有三档，`paid/removed` 只能塞进 notes；缺图、状态与 `free` 不一致要靠人工发现。
- **根因**：口径停留在文档/口头，没有进入构建断言。
- **可复用规则**：状态枚举与一致性写进 `build.js`：`verified` 必须 `free=true` 且有 `officialUrl`；`paid/removed/dead` 必须 `free=false`；带 `recheck` 的线索校验日期/结论/渠道/证据；`recheck-evidence.json` 单独校验；免费缺图只对 B 站来源进「待补图」，其余直接 fail。
- **下次怎么做**：改任何状态口径先改 `build.js`，再改数据；提交前跑 `node scripts/build.js`，页面改动另跑 `--page` 并用 SHA256 验证数据构建不改页面。

## 6. 截图与占位图：宁缺毋滥

- **现象**：GitHub Quest System 的 OG 图下载 429；部分网盘资源没有可核实的官方图。
- **根因**：外链图有速率限制，且授权不明。
- **可复用规则**：只用可下载的真实 JPEG/PNG/WebP；下载失败就不并入主目录，绝不生成占位图或热链；免费条目缺图进「待补图」报告。
- **下次怎么做**：先确认官方页与图片可获取，再决定是否入主目录；`build.js` 继续校验图片魔数与尺寸。

## 7. 数据与页面隔离：一条命令一个职责

- **现象**：数据构建与页面重建混在一起会让 `index.html` 无故变动。
- **根因**：构建入口没有区分「数据」与「页面」。
- **可复用规则**：新增数据只跑 `node scripts/build.js`；只有改 `src/` 才跑 `--page`；复核脚本 `recheck.js` 末尾串跑数据构建，不碰页面。
- **下次怎么做**：改数据后构建并比对 `index.html` SHA256；改模板后重建页面，再跑一次纯数据构建确认页面哈希不变。

## 8. 二次反查必须给四档结论，不能留「待核实」

- **现象**：二次反查的线索中，有的只能确认「查过所有公开渠道仍找不到」，如果继续留在 `pending`，会无限循环复核。
- **根因**：状态枚举缺少「渠道穷尽」这一档，`pending` 被当成垃圾桶。
- **可复用规则**：每条结论必须落 `free/paid/removed/unverifiable` 之一；`unverifiable` 必须列 `channels`（查过哪些渠道）、`checkedAt`、`note`，页面写「查过但无法确认」而不是「没查」；线索本身不删除。
- **下次怎么做**：先跑 `recheck.js` 读 evidence；人工多形态搜索（原名 + 英文名/拼写变体/缩写/中日文）后逐条写 verdict；改判后跑 `node scripts/build.js`，再抽查 `#/bilibili/unverifiable` 是否能看懂证据。

## 9. 菜单与分片：先定路由再定数据

- **现象**：B 站信息源与原生资源混在一个长页面，筛选互相污染，首屏要载全量数据。
- **根因**：页面没有「视图」概念，数据只有一个 `assets.js`。
- **可复用规则**：菜单负责范围（资源/工具/B 站/清单），视图内筛选负责维度；两者都进同一 hash；每个视图一个分片，进入才注入 `<script src>`，同分片缓存不重复请求；`file://` 下不用 `fetch`。
- **下次怎么做**：新增视图先加 `ROUTES`、分片映射、`counts`，再写渲染；`build.js` 会校验路由唯一、分片可解析、`index.html` 不含内联条目。

## 10. GitHub 未认证 API：靠 search 字段，不逐仓库打详情

- **现象**：core 限额 60 次/小时，逐仓库取详情会瞬间打满；search 限额 10 次/分钟。
- **根因**：详情接口按仓库计数，search 结果本身已带 stars/forks/pushedAt/license/archived/topics。
- **可复用规则**：`per_page=100` + 少量 topic/关键词查询覆盖；只对少数重点仓库补详情；命中 403/429 立即停，标「未获取」，不换账号、不刷接口。
- **下次怎么做**：先算查询数上限再抓；采集完把 `queries` 写进 `meta`；`build.js` 校验 stars/forks 整数、日期与活跃度一致、归档与推荐互斥。

## 11. 插件推荐不能只看最近提交时间

- **现象**：按「超 12 个月未更新就存疑」一刀切，会误杀社区仍在用、只是作者不再发版的成熟插件。
- **根因**：把「维护活跃」当成「可用性」的唯一代理指标，忽略人气样本。
- **可复用规则**：双口径判定——活跃度定档，人气（stars ≥ 300 或分组前 20%）决定是否仍推荐；久未更新但高人气保留推荐并标注最后提交、UE 版本、改编译风险；归档一律不默认展示。
- **下次怎么做**：默认按综合热度排序（`stars*2 + forks + max(0,30-openIssues)`，同分按活跃度再按名称）；筛选提供「仅活跃」「仅高人气」「排除归档」；页面显示 stars 与评价数样本量。

## 13. GitHub 补图：OG 429 不是终点，但必须有止损

- **现象**：GitHub 补图时一批 OG 图接口 429，直接放弃会把覆盖率停在较低水平；当前终态已到 348/349，GitHub 仅 1 条缺图。
- **根因**：只依赖单一 OG 端点，且 Node 默认不跟随 302，README 里的 GitHub assets 图会被误判失败。
- **可复用规则**：OG 429 时随机退避重试一次；仍失败则读 README 首图（跳过 badge/SVG），相对路径按 raw 解析；`github.com/.../assets/...` 要跟随 302；仍无图就保留占位并写入 `meta.imageMissing` 与待补图清单，不伪造。每张图记录 `imageSource`（OG / README:branch / raw 路径）。
- **下次怎么做**：先按上述顺序跑，单张最多 2 次 OG 重试；覆盖率按「实际本地文件」重算，不按字段是否为空。

## 14. 限额内补 GitHub 详情：详情 + release 用 API，.uplugin 走 raw

- **现象**：未认证 core 只有 60 次/小时；逐仓库取详情会打满，且很多 `.uplugin` 根本没有 `EngineVersion`。
- **根因**：把「补齐字段」等同于「每个仓库都要打详情」；`.uplugin` 可以走 `raw.githubusercontent.com` 不占 API。
- **可复用规则**：只对重点仓库（久未更新但高人气、活跃高星、主推荐）做 `repo` + `releases/latest`（每仓 2 次），命中限额余量 ≤3 即停；`lastRelease` 允许「tag（YYYY-MM-DD）」「无 release」「未获取」三种取值；UE 版本先读 `.uplugin` 的 `EngineVersion`，没有就退到 README 明示版本，仍无则「未获取」并注明来源。
- **下次怎么做**：先读 `x-ratelimit-remaining` 再排优先级；`meta.enrich` 记录调用数、剩余额度与停止原因；构建校验接受三种 release 格式。

## 15. 最后一轮作者名反查：用「几何体/贴图数量」做指纹

- **现象**：原 6 条 unverifiable 只剩网盘线索；泛化关键词搜索一直无结果。最后一轮 1 条命中改判 paid，5 条结案保留。
- **根因**：一直用资源中文描述搜索，没有把视频简介里的硬特征（73 几何体 / 271 贴图 / 93 几何体 / 84 贴图）当作指纹去比对官方商品页。
- **可复用规则**：最后一轮用「数量特征 + 英文原名 + 作者名」组合搜索；命中官方页后核对型号/数量/引擎版本，一致才改判；证据不足时保留 unverifiable，并在备注写清最后一轮渠道与结束追溯。相同视频里的两条资源要分别判定，不能因为一条命中就推定另一条。
- **下次怎么做**：先提取可量化特征，再查 Fab/UE Marketplace 商品页与 ArtStation；每条都有终态，不再重复追同一线索。

## 16. 付费补录的许可盲区：能买不等于能商用

- **现象**：Fab 商品页的许可条款显示 `-`，价格、评分、评价数都能看到，但 Personal/Professional 与商业游戏范围没有展开；本轮新增 13 条付费全部属于这种情况。
- **根因**：把「有购买入口」当成「许可已确认」；商品页默认视图不展示完整条款，结算页才会出现具体授权。
- **可复用规则**：许可拿不到就写「未获取（Fab 商品页许可条款显示「-」，购买前需在结算页确认 Personal/Professional 与商业游戏范围）」，不推断、不默认「可商用」；`build.js` 只要求字段非空，不把未获取当成错误。
- **下次怎么做**：先查商品页许可区、卖家 FAQ 与官方文档；仍无就保留「未获取」，在报告第 5 节单列条数；付款前必须在结算页确认，不拿「能买」推导授权。

## 17. 付费样本量阈值：高分不等于口碑

- **现象**：本轮新增 13 条付费评分落在 4.7–5.0，但评价数 ≥50 的只有 10/13；`Modern Guns` 只有 5 条评价，仍是 4.7 分。全站付费项里评价数 <10 的有 15 条。
- **根因**：小样本容易产生高分假象；只按评分排序会把「少数人满意」当成「普遍可靠」。
- **可复用规则**：评价数 <10 一律标「样本少」，页面和报告都显示评分 + 评价数；选品优先评价数 ≥50 且评分 ≥4.5；不因为 5.0 忽略样本量。
- **下次怎么做**：先按 reviews 过滤，再看 rating；`lowSamplePaid` 继续由 `build.js` 统计并在报告 3.3 单列；推荐语不写「口碑极佳」，只写可核实的样本。

## 18. 口径差异不是数据矛盾：先对齐口径再改文档

- **现象**：同一批数据出现 `epic-samples` 来源 41 条 vs `epic-samples.json` 34 条、GitHub 来源 129 条 vs GitHub 视图 84 条、B 站原始线索 51 条 vs 去重资源 48 条、全条目归档 5 条 vs GitHub 归档 2 条。看起来像矛盾，实际是统计范围不同。
- **根因**：来源计数、采集文件、原始提及、去重资源、全条目归档、GitHub 归档是六种口径；文档如果没有写明范围，就会被读成同一件事。
- **可复用规则**：总数、免费/付费、截图数只认 `data/core.js` 的 `counts/stats`；口径差异在报告正文显式标注（如「41 = 34 净新增 + 7 条既有」）；不强行改数让两处相等，也不把口径差异报成矛盾。
- **下次怎么做**：先确认数字的口径，再改文档；生成报告后跑 `node scripts/report.js` 的一致性断言；文档巡检用 grep 搜旧总量数字并逐条清掉。
